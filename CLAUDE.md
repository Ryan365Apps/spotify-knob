# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Radial** — a desk knob that controls Spotify playback directly against the Spotify Web API. No PC companion process, no cloud of our own. The repo carries **two tracks**, and Ryan states at the start of each session which one is active. Do not mix their scopes; if the session doesn't say and the work is ambiguous, ask.

- **Standard build** — a one-off device for Ryan's desk on the Waveshare ESP32-S3-Knob-Touch-LCD-1.8 (360×360 round screen, rotary encoder, no push switch). This is the working device and the software proving ground. Governed by `BUILD.md`, `firmware/`, `design/`, `tools/`.
- **The halo project** — the first product, a halo product in the automotive sense: a high-end device that establishes engineering credentials before more mainstream ones, the sports car before the family car. The device itself is called the **60** (sixty detent positions, sixty units). Same software as the standard build, a very different hardware scope (135 mm machined dial, magnetic detents, custom ring motor). Governed by the premium doc set: `docs/VISION.md`, `docs/DECISIONS.md`, `docs/PREMIUM-BOM.md`, `docs/CAD-BRIEF.md`, `docs/COMMERCIAL-BRIEF.md`, `docs/COMMERCIAL-FEASIBILITY.md`.

The intended progression: basic device → custom device → real product. The standard build exists to get hardware on the desk and try software out; the 60 is where that matures into a product. The premium docs describe hardware that doesn't exist yet — never apply their constraints to standard-build firmware, and never let the Waveshare board's limits quietly shape a decision about the 60.

## Hard rules

1. **Never use a bare reference.** In documents and in chat, never cite a shorthand ID without restating what it means. Not "R4" — write "R4, the requirement to toggle play/pause from the screen". Same for wave numbers, decision numbers, screen codes (write "screen 09 A, the access-point config screen"), moodboard shorthand, section numbers. The reference must carry its meaning with it every time it appears.
2. **No string typed by a human may ever become a keystroke.** The device will be a BLE HID keyboard; its HTTP config server is LAN-reachable. Chords are always an enum/dropdown, never free text. BUILD.md section 6 states this in full; do not weaken it in any code or doc.
3. **`spotify_tokens.json` holds a live refresh token.** Never commit it, print its contents, or serve it. `tools/serve_sim.py` deliberately exposes only the client ID.
4. **Do not re-litigate settled decisions.** `docs/DECISIONS.md` is the decision index for the 60 — items marked Decided need new evidence to reopen, not a fresh argument. The standard build's equivalent record is BUILD.md itself.

## Communication style

Lead with the answer, in plain English, short. Detailed models and reasoning go into the docs, not the chat reply. Offer to put detail in a doc rather than writing a long response.

## The design flow (this is how the project works)

The simulator leads; the docs follow. UX is designed by iterating [design/simulator.html](design/simulator.html) interactively — it is the only place interactions can be felt. `design/screens.html` (regenerated by Ryan in Claude desktop; revision letters bump) and `BUILD.md` record decisions after they survive contact.

**After any interaction change, update all three in the same turn:** simulator.html, screens.html, BUILD.md. When screens.html changes on disk, diff it against git and sync the simulator and BUILD.md to match.

`BUILD.md` is edited in place, not appended to — it describes the current plan, never a changelog.

## Commands

Simulator (mock playback by default, Live mode does Spotify PKCE):

```
python tools/serve_sim.py        # serves design/ on http://127.0.0.1:8888
```

Quirks: it must be started manually after reboot and dies with its console. Windows lets zombie instances double-bind port 8888 — kill every serve_sim python before restarting. The browser caches the page; hard refresh (Ctrl+F5) when changes seem missing. It also types the Wispr hotkey chord on the PC, standing in for the future BLE keyboard.

Spotify tooling:

```
python tools/spotify_auth.py --client-id <id>   # PKCE flow, writes spotify_tokens.json, runs pre-flight
python tools/preflight_endpoints.py             # re-test every endpoint the build depends on
python tools/check_devices.py                   # list playback devices + supports_volume
```

Firmware (ESP-IDF v5.5.x, `idf.py` directly — no PlatformIO):

```
cd firmware/knob
idf.py build
idf.py flash monitor
```

Known-good pinned component versions are in BUILD.md section 4 (toolchain and dependencies). `espressif/button` is required even though the board has no button — `esp_lvgl_port` hard-fails without it.

## Hardware facts that bite

All verified against the schematic (BUILD.md section 3, hardware facts):

- **There is no knob button, no BOOT button, no RESET button.** Recovery from a failed flash is USB cable orientation (it selects which MCU enumerates), not a button.
- USB HID and the flashing port share the same peripheral — firmware must use BLE HID, never USB HID, or the board can be bricked.
- Touch (CST816) and haptics (DRV2605) share one I2C bus — one `i2c_master` handle, two devices.
- The screen has no tearing-effect line connected; don't configure the panel driver to expect one.
